🗄️ The core problem

Internal billing system
Third-party tax platform

Revenue reported by the internal billing system does not match revenue reported by the third-party tax platform (Avalara / Vertex / TaxJar). Finance must determine the correct sales tax liability — but the root cause is often subtle, and the mismatch doesn't self-resolve.

🕵️ Why the mismatch persists (root causes)

1 · Taxonomy drift
New SKUs created without a tax category (or wrong one). Internal defaults to exempt, tax platform defaults to taxable. Manually curated across a large, changing catalog → gaps build silently.
2 · Regulation change
A state changes what's taxable (e.g. digital services). The rule changed, but internal classification didn't catch up — an error appears with zero human action.

Key distinction: timing differences auto-reconcile at year-end, but classification differences do not — they need a human to determine which side is correct and true-up or refund.

👤 Involved users

Primary

Finance / Tax Analyst

Financially literate, not a tax attorney. Needs to understand why numbers differ, see evidence, confirm/correct, and get to the right liability fast.

Approver

Tax / Revenue Controller

Owns the liability decision. Needs confidence + an audit trail before approving a true-up or filing.

Secondary

Catalog / RevOps

Maintains the SKU taxonomy. Needs a clear signal when a category is wrong and what to fix it to.

System

Third-party tax platform

Avalara / Vertex / TaxJar — external source of rules + computed liability. A system, not an interactive user.

It's an evergreen problem — manual taxonomy curation doesn't scale as the catalog and jurisdictions grow. Not a one-time fix.

3 specialized agents that prevent + detect + self-correct

Agent 1 · Taxonomy Guardian

Maintains SKU → tax category

Continuously reviews existing SKUs for correctness, and applies a category to new SKUs (instead of leaving them blank/default).

Agent 2 · Regulatory Watcher

Tracks external rule changes

Watches state/jurisdiction rule changes. Notifies Agent 1 (fix taxonomy) and Agent 3 (proactive heads-up to Finance).

Agent 3 · Finance-facing Tax Ops PM

Human-facing interface

Runs the reconciliation loop, checks 3rd-party config when debugging, investigates & explains which side is correct, alerts Finance, escalates edge cases, tracks to closure.

One reactive debugging agent

The single agent

Investigate & resolve when Finance raises a case

Pulls both sides' classifications, determines which is correct, explains it with evidence, and recommends a true-up/refund. Reactive only — it fixes the case you bring it, but doesn't prevent the next one.

Limitations: No prevention, no self-correction. Same taxonomy drift and rule-change gaps keep happening. Finance has to keep noticing issues and bringing them to the agent. 41% of cases recur from a prior fix.

⭐ Why multi-agent is preferred

Prevents recurrence. Keeps the taxonomy correct and rules fresh, so the same issue doesn't come back.
Self-corrects. Resolutions feed back into Agent 1's taxonomy, so the system improves over time.
Proactive. Finance gets a heads-up on rule changes before a surprise tax bill or audit flag.
Right-sized. Only 3 agents, each with a distinct job, + a cheap background check. Low latency, not over-engineered.

🎯 Recommended: Multi-agent

Because the core pain is recurrence, not just today's fix. Multi-agent prevents, detects, and self-corrects — while still keeping a human-facing interface (Agent 3) and escalating edge cases to a person.

Self-correction needs human prompt. Agents suggest and automate the grunt work; the human confirms judgment calls on ambiguous items (bundles, edge cases). Safe + auditable.
